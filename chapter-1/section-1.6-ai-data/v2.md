## 1.6 Data Science and Artificial Intelligence Components

LabyrinthAI uses data for two opposite purposes:

- **Real data teaches the system.** Labelled network traffic trains the classifier to
  separate legitimate users from attackers, and novices from skilled attackers.
- **Fake data deceives the attacker.** Generated emails, documents, and records fill the
  Digital Twin so it mirrors the real network.

A third source appears once the environment is live: session logs from attackers inside
the Digital Twin, used to refine the classifier after its initial training.

### 1.6.1 Dataset Description and Source

| Dataset | Source / Owner | Size / Records | Features / Data Type | Target / Labels | License / Access |
|---|---|---|---|---|---|
| CSE-CIC-IDS 2018 | CSE and the Canadian Institute for Cybersecurity, University of New Brunswick | ≈16M flow records, 10 days; ≈6.5 GB CSV | 80 flow features (CICFlowMeter-V3); raw PCAP; host logs | `Label`: Benign or attack class, 7 categories | Free for academic use; citation required |
| Digital Twin session logs | Self-collected via Wazuh/ELK | Grows from Phase 2 | Commands, file access, timing, lateral movement | Skill tier, labelled by Red Team | Project-owned; isolated lab |
| Decoy corpus | Generated by Llama 3 (Ollama) and Faker | On demand | Emails, reports, employee and finance tables | Not applicable — system output | Project-owned; fully synthetic |

**Why this dataset.** KDD Cup 99 and NSL-KDD describe networks that no longer exist.
DARPA 98/99 is synthetic at packet level. CSE-CIC-IDS 2018 was captured from a victim
organisation of five departments, 420 clients, and 30 servers, attacked by 50 machines
running current tooling. Its attack categories — brute force, DoS, DDoS, web attack,
infiltration, botnet — match the behaviours LabyrinthAI must classify.

**Known limitations.** The dataset was assessed, not assumed. Four flaws drive the
preprocessing in Section 1.6.3:

- **Class imbalance.** Benign traffic dominates. Heartbleed and SQL Injection appear in
  tens of records. Accuracy alone cannot measure this task.
- **Label quality.** Engelen et al. (2021) documented mislabelled records, mainly in
  Infiltration. Classes are checked against the published capture schedule; untrustworthy
  classes are excluded with justification.
- **File defects.** Header rows repeat mid-file. Records duplicate. `Flow Bytes/s` and
  `Flow Packets/s` contain `Infinity` and `NaN`.
- **Environment specificity.** Addresses, ports, and timestamps describe one AWS capture,
  not attacker behaviour. Section 1.6.3 removes them.

### 1.6.2 Data Collection Method

| Collection Aspect | Planned Method / Decision |
|---|---|
| Source and acquisition | Download pre-extracted CSVs from CIC rather than re-deriving from PCAP. Keeps features consistent with published work used for comparison. Session logs arrive through the project SIEM. Decoy text is generated locally; no external API. |
| Sampling / coverage | All ten capture days retained, so every attack class is represented. Benign volume reduced only by the undersampling in Section 1.6.3, applied only to training data. |
| Labeling / annotation | Public labels come from the authors' attack schedule and are validated before use. Session labels are set by the Red Team, who execute each attack and know the ground truth. Decoy content needs no labels. |
| Permissions / ethics | The dataset is released for academic use and cited. It holds no personal data, being captured from a laboratory organisation. All self-collected traffic originates in an isolated lab, on project-owned machines, attacked by the project team. No live network, third party, or real person is involved. Names and figures inside the Digital Twin are fabricated. |
| Known collection bias | **Temporal** — tooling is from 2018; session logs compensate. **Environmental** — one AWS topology; environment features removed. **Operator** — a small Red Team may not generalise; attacks are scripted from standard tooling and operators rotated. |

### 1.6.3 Data Preprocessing

Every learned transformation is fitted on training data only, then applied unchanged to
validation and test data.

| Stage | Planned Operation | Reason / Leakage Control |
|---|---|---|
| Data quality checks | Remove repeated header rows. Drop duplicate records. Replace `Infinity` and `NaN` in the two rate features. Verify record counts against the capture schedule. | Duplicates are removed before splitting. A record in both training and test data inflates results without real generalisation. Non-finite values come from zero-duration flows and corrupt scaling. |
| Cleaning / transformation | Drop source and destination IP, source and destination port, `Flow ID`, `Timestamp`. Drop constant columns such as `Bwd PSH Flags`. Normalise label strings. | The main leakage control. Keeping the attacker's IP lets the model memorise which machine attacked, not what attacks look like; it then fails against any new attacker. Keeping `Timestamp` lets it exploit the fixed daily attack schedule. |
| Feature engineering | Keep behavioural families: duration, packet and byte counts, inter-arrival statistics, packet-length statistics, flag counts. Derive shape ratios such as forward-to-backward packets and bytes per packet. Reduce correlated pairs, keeping the interpretable member. | Behavioural features transfer to the Digital Twin; absolute volumes reflect the capture network. Interpretability is a requirement, not a preference: the SHAP/LIME layer must show the analyst a feature-level reason. |
| Scaling / encoding | Standardise numerical features, fitted on training data only. Encode the target numerically. Use the Llama 3 tokenizer for LLM text. | Fitting on the full corpus leaks the test distribution into training. The fitted scaler is saved and reused at inference, so live input is transformed identically. |
| Imbalance / augmentation | Undersample benign traffic. Oversample sparse attack classes with SMOTE. Weight classes during training. Merge or exclude classes too sparse to learn, stating the exclusion. | Applied to training data only. Resampling before splitting puts near-duplicates into the test set. Validation and test keep the natural distribution, because the false-positive rate in Section 1.6.6 is meaningless otherwise. |

**Decoy corpus quality gate.** Generated content is system output, not training input, so
it passes a separate check:

- **Internal consistency.** An employee named in an email must exist in the directory.
  File paths must resolve. One contradiction tells the attacker the environment is fake.
- **No leaked real data.** Content is screened for personal data reproduced from the
  model's training corpus.
- **No credential collision.** No fabricated credential may match a real one used in
  project infrastructure.
