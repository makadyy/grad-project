## 1.6 Data Science and Artificial Intelligence Components

LabyrinthAI depends on data in two distinct ways, and this section separates them
deliberately because they serve opposite purposes.

The first is **real data used to teach the system**: labelled network-traffic records
that train the behavioural classification engine to distinguish a legitimate user from
an attacker, and a novice attacker from a skilled one. The second is **synthetic data
used to deceive the attacker**: the fabricated emails, documents, and database records
that populate the Digital Twin so that it is indistinguishable from the real corporate
network it mirrors.

A third source appears once the deception environment is live: the **session logs
generated by attackers inside the Digital Twin itself**, which are collected
continuously and used to refine the classifier beyond its initial public-dataset
training.

### 1.6.1 Dataset Description and Source

| Dataset | Source / Owner | Size / Records | Features / Data Type | Target / Labels | License / Access |
|---|---|---|---|---|---|
| CSE-CIC-IDS 2018 | Communications Security Establishment (CSE) and the Canadian Institute for Cybersecurity (CIC), University of New Brunswick | ≈16 million bidirectional flow records across 10 capture days (14 Feb – 2 Mar 2018); ≈6.5 GB as CSV, >200 GB including raw PCAP | 80 numerical flow features extracted with CICFlowMeter-V3 (packet counts, byte counts, inter-arrival timings, flag counts, flow duration), plus raw PCAP and Windows/Ubuntu host logs | `Label` column: `Benign` or a named attack class across 7 categories — Brute Force, DoS, DDoS, Web Attack, Infiltration, Botnet, Heartbleed | Publicly released for academic and research use, distributed via AWS S3 and the CIC website; free of charge, attribution to the originating publication required |
| Digital Twin session logs (self-collected) | Generated in-house by the project's own decoy infrastructure (Wazuh/ELK, containerised decoy services) | Grows continuously from Phase 2 onward; volume determined by Red Team activity | Session records: commands issued, services touched, file accesses, lateral-movement attempts, timing between actions | Attacker skill tier and intent, labelled by the project's Red Team from known attack scripts | Project-owned; generated entirely inside an isolated laboratory, no third-party or personal data involved |
| LLM-generated decoy corpus (synthetic) | Produced by the project using Llama 3 served locally via Ollama, with the Faker library for structured field values | Generated on demand; scaled to the size of the simulated organisation | Unstructured text (corporate emails, memos, reports) and structured records (employee tables, financial spreadsheets, credential stores) | Not applicable — this data is an output of the system, not training input | Project-owned; fully synthetic, contains no real personal or corporate information |

**Justification of dataset choice.** CSE-CIC-IDS 2018 was selected over older
alternatives such as KDD Cup 99 and NSL-KDD, which are widely criticised for reflecting
network conditions that no longer exist, and over DARPA 98/99, which is synthetic at the
packet level. CSE-CIC-IDS 2018 was captured from a realistic victim organisation of five
departments, approximately 420 client machines and 30 servers, attacked by a dedicated
infrastructure of 50 machines running current tooling. Its attack taxonomy — brute force,
DoS, DDoS, web attack, infiltration, botnet — corresponds directly to the attacker
behaviours LabyrinthAI is designed to observe and classify inside the Digital Twin.

**Known limitations.** The dataset's suitability was assessed rather than assumed, and
four limitations are acknowledged in advance because they drive the preprocessing design
in Section 1.6.3:

1. **Severe class imbalance.** Benign traffic dominates the corpus, while several attack
   classes are extremely sparse — Heartbleed and SQL Injection are represented by only
   tens of records. Accuracy is therefore an inadequate primary metric, and the classes
   most relevant to a skilled-attacker profile are the rarest.
2. **Label quality.** Independent re-analysis of the dataset, notably Engelen et al.
   (2021), has documented mislabelled records, particularly within the Infiltration
   class. Attack categories will be validated against the published capture schedule
   before use, and any class that cannot be trusted will be excluded with justification
   rather than silently retained.
3. **Structural defects in the CSV distribution.** Several files contain repeated header
   rows in the middle of the data, duplicated records, and non-finite values
   (`Infinity`, `NaN`) in the derived rate features `Flow Bytes/s` and `Flow Packets/s`.
4. **Environment specificity.** The capture reflects one particular AWS-hosted topology.
   Features tied to that environment — addresses, ports, timestamps — describe *where and
   when* the capture happened rather than *how an attacker behaves*, and are removed for
   the reasons given in Section 1.6.3.

### 1.6.2 Data Collection Method

| Collection Aspect | Planned Method / Decision |
|---|---|
| **Source and acquisition** | CSE-CIC-IDS 2018 is obtained by direct download of the pre-extracted CSV flow files from the CIC distribution, rather than re-deriving features from the raw PCAP archive. This keeps the feature set consistent with the published dataset and with prior work used for comparison in Chapter 2. Session logs are acquired through the project's own centralised SIEM (Wazuh/ELK), which aggregates events from every containerised decoy. Decoy content is generated locally by Llama 3 through Ollama, with no external API dependency. |
| **Sampling / coverage** | All ten capture days are retained rather than a single day, so that every attack category is represented and the classifier is not fitted to one day's traffic mix. Where the volume of benign flows is reduced for tractability, reduction is performed by controlled undersampling described in Section 1.6.3 and applied only to the training partition. |
| **Labeling / annotation** | Public-dataset labels are supplied by the dataset authors and derived from a documented attack schedule; they are used as-is after the validation check described above. Labels for self-collected session data are assigned by the project's Red Team, who execute each attack scenario and therefore know the ground truth of every session, so labelling is deterministic rather than a matter of analyst judgement. Synthetic decoy content requires no labels, as it is system output rather than training input. |
| **Permissions / ethics** | CSE-CIC-IDS 2018 is released for academic use and is cited accordingly; it contains no personally identifying information, having been captured from a purpose-built laboratory organisation rather than a live network. All self-collected traffic originates inside an isolated virtual laboratory, from machines owned and operated by the project team, attacked by the project team. No live corporate network, third-party system, or real individual's data is captured at any stage. Decoy content is fabricated in full, and personal names, addresses, and financial figures appearing inside the Digital Twin are generated values that correspond to no real person. |
| **Known collection bias** | Three biases are recognised. **Temporal bias**: the public dataset represents attack tooling as it existed in 2018, so techniques introduced since are absent; self-collected session data is used to compensate. **Environmental bias**: the capture topology is a single AWS deployment, addressed by removing environment-identifying features. **Operator bias**: self-collected sessions are produced by a small Red Team whose habits may not generalise, mitigated by scripting attacks from established tooling (Metasploit, Nmap, BloodHound) and varying operators across sessions rather than relying on one person's technique. |

### 1.6.3 Data Preprocessing

The pipeline below is defined before training begins. Every learned transformation —
scaling parameters, encoding maps, resampling — is fitted on the training partition only
and then applied unchanged to validation and test data, so that no information from
evaluation data can influence the model.

| Stage | Planned Operation | Reason / Leakage Control |
|---|---|---|
| **Data quality checks** | Remove repeated header rows embedded within the CSV files; drop exact duplicate flow records; replace `Infinity` and `NaN` values in `Flow Bytes/s` and `Flow Packets/s`; verify each file's record count and class distribution against the published capture schedule. | Duplicates are removed *before* partitioning, because an identical record appearing in both training and test data inflates measured performance without any real generalisation. Non-finite values arise from zero-duration flows and would otherwise propagate through scaling and corrupt every feature. |
| **Cleaning / transformation** | Drop identifier and environment-specific columns — source and destination IP address, source and destination port, `Flow ID`, and `Timestamp`. Drop zero-variance columns that are constant across the entire corpus (for example `Bwd PSH Flags`, `Fwd URG Flags`). Normalise class-label strings to a consistent naming scheme. | This is the most important leakage control in the pipeline. Retaining the attacker's IP address lets the model achieve near-perfect accuracy by memorising *which machine* attacked rather than *what an attack looks like*, and such a model fails immediately against any new attacker. Retaining `Timestamp` allows the model to exploit the fixed daily attack schedule instead of learning behaviour. |
| **Feature engineering / extraction** | Retain the CICFlowMeter behavioural feature families — flow duration, forward and backward packet and byte counts, inter-arrival time statistics, packet-length statistics, and TCP flag counts. Derive ratio features that describe interaction shape independently of volume, such as forward-to-backward packet ratio and bytes per packet. Reduce correlated feature pairs, retaining the more interpretable member of each pair. | Behavioural features transfer to the Digital Twin environment, whereas absolute volume figures reflect the capture network's capacity. Interpretability is a functional requirement rather than a preference: the XAI layer (Section 1.6.4, SHAP/LIME) must present a feature-level justification to the SOC analyst, and an explanation expressed in engineered features that a human cannot interpret would defeat that requirement. |
| **Scaling / encoding / tokenization** | Apply standardisation to numerical features, fitted exclusively on the training partition. Encode the multi-class target label numerically. For text handled by the LLM component, apply the tokenizer supplied with the Llama 3 model rather than a separately fitted vocabulary. | Fitting a scaler on the full corpus leaks the test set's distribution — its mean and variance — into training, producing optimistic results that do not survive deployment. The scaler fitted on training data is serialised and reused unchanged at inference time inside the live system, so that production input is transformed identically to training input. |
| **Imbalance / augmentation** | Address imbalance with a combined strategy: controlled undersampling of the dominant benign class, oversampling of sparse attack classes using SMOTE, and class weighting during training. Classes too sparse to support meaningful learning after inspection are either merged into a coherent parent category or excluded, with the exclusion stated explicitly. | Applied to the **training partition only**. Generating synthetic minority samples before partitioning places near-duplicates of training records into the test set and produces results that cannot be reproduced. Validation and test partitions retain the natural class distribution, because the false-positive rate reported in Section 1.6.6 is only meaningful when measured against realistic proportions. |

**Preprocessing of the synthetic decoy corpus.** Content generated for the Digital Twin
is subject to a separate quality gate rather than the pipeline above, since it is not
training input. Generated artefacts are checked for **internal consistency** — an
employee named in a fabricated email must exist in the fabricated employee directory,
and referenced file paths must resolve inside the decoy filesystem — because an attacker
who encounters a contradiction identifies the environment as artificial and disengages.
Generated content is also screened to confirm that no real personal data has been
reproduced from the model's training corpus, and that no fabricated credential
inadvertently matches a genuine one used anywhere in the project infrastructure.

**1.6.3 — "here is how I clean the data before training."**
This is the strongest part and the most defensible in a discussion. Two ideas carry it:

- **Leakage** — accidentally letting the model see, during training, information it won't
  have in real life. It then scores brilliantly in your tests and fails in reality. Your
  biggest one: if you leave the attacker's IP address in the data, the model just memorises
  "192.168.x.x is the bad guy" instead of learning what attacking *looks like*. You'd get
  99% accuracy and a worthless system. So you delete the IPs, ports and timestamps.
- **Imbalance** — almost all the records are normal traffic. A model that answers "normal"
  every single time is ~83% accurate and catches nothing. So you rebalance — but **only the
  training data**, never the test data, otherwise you're grading yourself on a fake exam.
