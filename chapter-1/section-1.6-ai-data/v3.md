## 1.6 Data Science and Artificial Intelligence Components

LabyrinthAI uses data for two opposite purposes:

- **Real data teaches the system.** Recorded network traffic, already marked as normal or
  attack, trains the classifier to tell legitimate users from attackers, and novices from
  skilled attackers.
- **Fake data deceives the attacker.** Generated emails, documents, and records fill the
  Digital Twin so it looks like the real network.

A third source appears once the Digital Twin is running. Every attacker who enters is
recorded: the commands they run, the files they open, the time between their actions.
One attacker's visit produces one **session log**. These logs are the project's own data,
collected from its own system, and are used to improve the classifier beyond what a public
dataset from 2018 can teach it.

### 1.6.1 Dataset Description and Source

| Dataset | Source / Owner | Size / Records | Features / Data Type | Target / Labels | License / Access |
|---|---|---|---|---|---|
| CSE-CIC-IDS 2018 | CSE and the Canadian Institute for Cybersecurity, University of New Brunswick | ≈16M connection records, 10 days; ≈6.5 GB CSV | 80 measurements per connection, extracted by CICFlowMeter-V3; raw packet captures; host logs | `Label`: Benign, or one of 7 attack types | Free for academic use; citation required |
| Digital Twin session logs | Collected by the project through Wazuh/ELK | Grows from Phase 2 onward | Commands run, files opened, timing, movement between machines | Attacker skill level, set by the Red Team | Project-owned; isolated lab |
| Decoy corpus | Generated by the project using Llama 3 (via Ollama) and Faker | Generated on demand | Emails, reports, employee and finance tables | None — this is output, not training input | Project-owned; fully invented |

**Why this dataset.** KDD Cup 99 and NSL-KDD describe networks that no longer exist.
DARPA 98/99 was generated artificially rather than captured. CSE-CIC-IDS 2018 was recorded
from a real victim organisation of five departments, 420 client machines, and 30 servers,
attacked by 50 machines running tools still in use. Its attack types — brute force, DoS,
DDoS, web attack, infiltration, botnet — are the same behaviours LabyrinthAI must
recognise.

**Known limitations.** The dataset was checked, not assumed. Four flaws shape the cleaning
steps in Section 1.6.3:

- **Class imbalance.** Most records are normal traffic. Some attacks appear only tens of
  times. A model can therefore score highly while catching nothing.
- **Label quality.** Engelen et al. (2021) found records marked with the wrong attack type,
  mostly in the Infiltration class. Each attack type is checked against the schedule the
  authors published; any type that cannot be trusted is excluded, and the exclusion stated.
- **File defects.** Column headings repeat in the middle of some files. Some records are
  exact copies of others. Two speed columns, `Flow Bytes/s` and `Flow Packets/s`, contain
  `Infinity` and `NaN` where a connection lasted no measurable time.
- **Environment specificity.** Addresses, port numbers, and timestamps describe the one
  network that was recorded, not how attackers behave. Section 1.6.3 removes them.

### 1.6.2 Data Collection Method

| Collection Aspect | Planned Method / Decision |
|---|---|
| Source and acquisition | Download the ready-made CSV files from CIC rather than re-processing the raw packet captures. This keeps the 80 measurements identical to those used in the published studies compared against in Chapter 2. Session logs reach the project through Wazuh/ELK, the system that gathers events from every decoy. Fake content is generated on project machines; no external service is called. |
| Sampling / coverage | All ten recording days are kept, so every attack type is present. Normal traffic is reduced only by the step described in Section 1.6.3, and only in the training portion. |
| Labeling / annotation | Public labels come from the schedule the dataset authors followed when running their attacks, and are checked before use. Session logs are labelled by the Red Team, who run each attack themselves and therefore know exactly what happened. Fake content needs no labels. |
| Permissions / ethics | The dataset is published for academic use and is cited. It contains no personal information, having been recorded from a purpose-built laboratory organisation rather than a live company. All traffic the project records itself comes from an isolated laboratory, on machines the team owns, attacked by the team. No live network, outside organisation, or real person is involved. Every name and figure inside the Digital Twin is invented. |
| Known collection bias | **Age** — the tools used are from 2018, so newer techniques are missing; the project's own session logs cover them. **Environment** — one network was recorded, so features describing that network are removed. **Operator** — a small Red Team may attack in a recognisable style; attacks are therefore scripted from standard tools and the operator is rotated. |

### 1.6.3 Data Preprocessing

Anything the pipeline learns from the data — averages used for scaling, encodings,
resampling — is calculated on the training portion alone, then applied unchanged to the
validation and test portions.

| Stage | Planned Operation | Reason / Leakage Control |
|---|---|---|
| Data quality checks | Remove repeated column headings. Delete records that are exact copies. Replace `Infinity` and `NaN` in the two speed columns. Check record counts against the published schedule. | Copies are deleted before the data is split. The same record in both training and test data makes results look better without the model having learned anything. The impossible speed values come from connections of zero length and would spread through every later calculation. |
| Cleaning / transformation | Remove the columns that identify machines rather than behaviour: source and destination IP address, source and destination port, `Flow ID`, and `Timestamp`. Remove columns holding the same value in every record. Make attack names consistent. | The most important step. If the attacker's IP address stays in the data, the model learns "traffic from that machine is an attack" instead of what an attack looks like. It scores near-perfectly in testing and fails against any attacker it has not seen. `Timestamp` lets it learn the attack schedule instead of the attacks. |
| Feature engineering | Keep the measurements that describe behaviour: how long a connection lasted, how many packets and bytes went each way, the gaps between packets, packet sizes, and TCP flag counts. Add two ratios — packets sent versus packets received, and average bytes per packet — which describe the shape of an exchange regardless of its size. Where two measurements always rise and fall together, keep the one easier to explain. | Behaviour transfers to the Digital Twin; raw volumes reflect the speed of the recorded network. Being able to explain a measurement is a requirement, not a preference: the SHAP/LIME layer must show the analyst which measurement caused a decision, and it cannot do that with a measurement no human understands. |
| Scaling / encoding | Rescale the numerical measurements to a common range, using averages calculated from the training portion only. Convert attack names to numbers. Use the tokenizer that ships with Llama 3 for generated text. | Calculating those averages across all the data lets the test data influence training, which makes results look better than the system will perform. The rescaling values are saved and reused when the system runs live, so live traffic is treated exactly like training traffic. |
| Imbalance / augmentation | Reduce the number of normal records. Create additional examples of rare attacks using SMOTE. Give rare attacks more weight during training. Merge or drop attack types with too few records to learn from, and say which were dropped. | Applied to the training portion only. Creating extra examples before splitting puts near-copies of training records into the test set. The validation and test portions keep the real mix of normal and attack traffic, because the false-alarm rate reported in Section 1.6.6 only means something when measured against realistic proportions. |

**Decoy corpus quality gate.** Generated content is what the system produces, not what it
learns from, so it is checked differently:

- **Internal consistency.** An employee named in a fake email must exist in the fake
  employee list. File paths must lead somewhere. One contradiction tells the attacker the
  environment is a trap.
- **No real data leaked.** Content is checked for personal details the language model may
  have reproduced from its own training data.
- **No credential collision.** No invented password may match a real one used anywhere in
  the project.

## Terms you'll be asked about

- **Dataset** — a big table. One row per recorded connection.
- **Record / row** — one connection between two machines.
- **Feature / measurement** — one column. Example: how many packets were sent.
- **Label** — the answer column. Normal, or which attack it was.
- **Classifier** — the model that reads a row and answers "normal or attack, and how skilled."
- **Training** — showing the model rows with answers so it learns the pattern.
- **Split** — cutting the data into three parts.
    - Training: it learns from this.
    - Validation: you tune settings on this.
    - Test: touched once, at the end, to get an honest score.
- **Session log** — the recording of one attacker's whole visit to your trap.
- **SMOTE** — makes extra copies of rare attacks so the model sees enough of them.
- **SIEM (Wazuh/ELK)** — the system that collects logs from everywhere into one place.
- **Tokenizer** — chops text into pieces a language model can read.

## The two ideas you must defend

- **Leakage — the model sees something it won't have in real life.**
    - Leave the attacker's IP in, and it memorises "that machine is bad."
    - Scores 99%. Catches nothing new.
    - So you delete IPs, ports, timestamps.
- **Imbalance — almost every record is normal traffic.**
    - Always answering "normal" scores ~83% and catches zero attacks.
    - So you rebalance training data only.
    - Rebalance the test set and you grade yourself on a fake exam.
